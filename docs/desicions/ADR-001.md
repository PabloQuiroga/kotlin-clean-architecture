# ADR 001: Adopción de Clean Architecture

## Estado
Aceptado

## Contexto
El sistema debe ser mantenible, testeable y resistente a cambios tecnológicos (por ejemplo, cambiar la base de datos o la API externa sin afectar la lógica de negocio).

## Decisión
Hemos decidido implementar la **Clean Architecture**, dividiendo el proyecto en tres capas estrictas: Dominio, Datos y API.

## Justificación
- **Independencia de infraestructura**: El Dominio no importa implementaciones de API, datos, persistencia ni Koin, lo que facilita reemplazar esos detalles.
- **Dependencia asíncrona acordada**: El contrato del repositorio usa `suspend` y `Flow` de Kotlin Coroutines según ADR-002. Esta dependencia de biblioteca se acepta explícitamente para la asincronía del proyecto.
- **Testeabilidad**: Al separar la lógica en "Casos de Uso", podemos testear el negocio sin necesidad de levantar una base de datos o una red real.
- **Mantenibilidad**: Cada cambio tiene un lugar específico; los errores de persistencia se arreglan en la capa de Datos y los errores de reglas de negocio en el Dominio.

## Consecuencias
- **Mayor cantidad de archivos**: Requiere la creación de interfaces y mapeadores (Mappers) para mover los datos entre capas.
- **Curva de aprendizaje**: El flujo de datos es más largo que en una arquitectura simple, pero mucho más robusto.
- **Dirección de dependencias**: El Dominio define el contrato; Datos lo implementa. La API/demo convierte los DTO a entidades antes de invocar los casos de uso.
